# Інструмент пакетної подачі форми

Веб-інструмент: оператор вводить список цілей і дані скарги, тул на кожну ціль
окремо заповнює форму. Результат по кожному рядку показує з кодом підтвердження
або причиною помилки. Невдалі рядки можна повторити.

## Що тулза робить

Робить:
- простий веб-інтерфейс для оператора (тип подачі, список цілей по рядку, Threat
  Type, Reason, файл-доказ з перевіркою типу і розміру до 2 МБ);
- масову обробку: N рядків = N окремих відправок, по одній на ціль;
- облік по кожному рядку: статус, підтвердження виду CF-XXXXXXXX або
  причина помилки; повтор невдалих рядків;
- запуск однією командою.

Свідомо НЕ робить (це частина відповіді, не недоробка):
- тул не обходить капчу. 2captcha та подібні сервіси не використовуються. Браузер
  відкривається видимим, капчу швидко вирішує людина. Обхід капчі це обхід захисту.
- не відправляє скаргу наосліп. Кожна скарга це юридичне твердження, тому фінальний
  Submit підтверджує людина у вікні браузера.

Якщо є офіційний масовий канал без капчі (типу програма для великих
обсягів DMCA), краще було б вести тул туди. Це питання я б уточнив першим.

## Стек

Python, Flask, Playwright, SQLite. Це мій робочий стек, Playwright для форми з
капчею, SQLite тримає стан між запусками без зайвої інфраструктури і рутини.

## Запуск

Варіант 1, локально:

    python -m venv .venv
    .venv\Scripts\activate (Windows) або source .venv/bin/activate
    pip install -r requirements.txt
    python -m playwright install chromium
    copy .env.example .env (Windows) або cp .env.example .env
    python app.py

Відкрити http://127.0.0.1:5000/

Варіант 2, Docker:

    docker compose up

Крок обробки (капча + Submit) вимагає вікна браузера, тому зручніше запуск локально (варіант 1), а не в контейнері.

## Як користуватись

1. На головній ввести тип, список цілей (один на рядок), Threat Type, Reason,
   прикріпити файл-доказ. Натиснути "Створити пакет".
2. На сторінці результату натиснути "Почати обробку". Для кожного рядка
   відкриється форма (уже заповнена). Вирішити капчу, натиснути Submit.
3. Тул читає код підтвердження або помилку і запише в таблицю. Сторінка
   оновлюється сама. Невдалі рядки можна повторити кнопкою "Повторити невдалі".

За замовчуванням тул працює з локальним макетом форми (`/mock-form`), щоб його
можна було безпечно перевірити без реального сервера.

## Налаштувати на реальну форму

1. У `.env` поставити `FORM_URL` на реальну адресу.
2. У `config.py` у `FORM_FIELDS` звірити селектори полів з реальною формою
   (відкрити форму, подивитись name полів).
3. Там же звірити `CONFIRMATION_CODE_PATTERN` і селектори `confirmation_code` та
   `error` під реальну відповідь форми: макетний `CF-XXXXXXXX` на реальній формі
   майже напевно інший. Інакше успішну відправку тул позначить як `sent_unverified`
   (подано, але код не розпізнано) - це безпечно (повтору не буде), але код не зчитається.
4. `HEADLESS` лишити `false`, без цього оператор не побачить капчу.

## Архітектура тули

    app.py            інтерфейс (ввід, результати, повтор) + локальний макет форми
    config.py         налаштування і селектори форми (місце для правок під форму)
    core/validation.py  розбір списку цілей, перевірка типу подачі і файлу
    core/db.py          SQLite: задачі, статуси, UNIQUE(batch_id, target)
    core/filler.py      Playwright: заповнення форми, оператор вирішує капчу і тисне Submit
    core/runner.py      черга: по одній відправці на ціль, backoff, ідемпотентність
    templates/, static/ сторінки і стилі
    tests/              тести валідації і черги (на фейкових браузері і заповнювачі)

Потік даних: ввід оператора -> валідація -> задачі в SQLite -> черга обробляє по
одній (людина підтверджує) -> результат і код у базу -> таблиця результатів.

## Мої рішення

- Масовість веде звичайний код-черга, не LLM. Заповнити форму N разів - точна,
  повторювана робота. LLM в цьому кейсі може призвести до втрат або помилок. LLM я б юзав там,
  де результат легко перевірити (чернетка тексту, класифікація і тд), тут же
  потрібна точність.
- Захист від подвійної відправки: дубль цілі відсікає UNIQUE(batch_id, target), а
  вже подані рядки (sent, sent_unverified) повторно не шлються. Повтор лише на
  тимчасовий збій і лише для читання результату на тій самій сторінці, щоб не
  стерти капчу.
- Якщо форму подано, але код не розпізнано (на реальній формі інший формат), рядок
  стає sent_unverified і повторно не шлеться. Так скарга не піде двічі.
- Збій видно: невдалий рядок дістає статус failed і причину. Один збій не валить
  увесь батч.
- "AI" у цьому тулі. Тул зібраний через Claude Code під моїм рев'ю, LLM не крутиться всередині відправки.

## Тести

    pip install pytest
    pytest

Тести перевіряють валідацію (розбір цілей, тип і розмір файлу) і чергу (одна
відправка на ціль, ідемпотентність, повтор невдалих) на фейкових браузері і
заповнювачі, без Playwright.

## Межі

- Селектори реальної форми треба звірити вручну (`config.py`): наосліп вони не
  вгадуються.
- Крок капчі і Submit вимагає присутності людини: це задумано.
- Docker піднімає інтерфейс, але крок обробки з видимим браузером краще запускати
  локально.
